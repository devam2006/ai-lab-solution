## 4. The Generated Python Program

*(The full code is located in `planner.py`. Below is the core logic engine.)*
*Note: As per the lab guidelines, I am identifying that the entirety of the core logic engine (`Action` class and `bfs_plan` function) in `planner.py` was generated by the LLM. The testing functions were subsequently organized and modified to execute Tests A, B, and C as required.*

```python
import collections
from typing import Set, List, Optional

class Action:
    def __init__(self, name: str, pos_pre: Set[str], neg_pre: Set[str], pos_eff: Set[str], neg_eff: Set[str]):
        self.name = name
        self.pos_pre = pos_pre
        self.neg_pre = neg_pre
        self.pos_eff = pos_eff
        self.neg_eff = neg_eff

    def is_applicable(self, state: Set[str]) -> bool:
        if not self.pos_pre.issubset(state):
            return False
        if not self.neg_pre.isdisjoint(state):
            return False
        return True

    def apply(self, state: Set[str]) -> Set[str]:
        new_state = state.copy()
        new_state.difference_update(self.neg_eff)
        new_state.update(self.pos_eff)
        return new_state

def bfs_plan(initial_state: Set[str], goal: Set[str], actions: List[Action]) -> Optional[List[Action]]:
    queue = collections.deque([(initial_state, [])])
    visited = set([frozenset(initial_state)])

    while queue:
        current_state, path = queue.popleft()

        if goal.issubset(current_state):
            return path

        for action in actions:
            if action.is_applicable(current_state):
                new_state = action.apply(current_state)
                new_state_frozen = frozenset(new_state)

                if new_state_frozen not in visited:
                    visited.add(new_state_frozen)
                    queue.append((new_state, path + [action]))

    return None
```

**Explain in your own words how logical reasoning and search work together to produce a plan:**
Logical reasoning defines the valid transitions in the environment—it determines which actions are legal in a given state and exactly how the state changes when an action is taken. Search provides the exploration strategy, systematically traversing these valid transitions to find a sequence of actions that connects the initial state to the desired goal state. In short, logic defines the graph of possible states, and search finds the shortest path through it.

## 7. Reflection Questions

**1. Why is it useful to specify action preconditions and effects before asking an LLM to write the planner?**
If you just tell an LLM "write a robot planner," it will guess how the world works and might make up rules. By giving it exact preconditions (what must be true before an action) and effects (what changes after), you put "guardrails" on the LLM. 
**Example:** Without these strict rules, the LLM might write code that lets the robot drop a package it isn't holding. By specifying the rules upfront, the LLM is forced to write code that strictly checks if the robot is `Holding(Package)` first.

**2. Give an example of an error that could occur if the planner failed to check an action’s preconditions.**
The planner could command the robot to do something physically impossible. 
**Example:** Imagine the robot is at Location A, and the package is at Location B. If the planner doesn't check the preconditions (which state they must be in the same location), it might tell the robot to execute `PickUp(Package)`. The robot would grab empty air at Location A, while the package sits untouched at Location B.

**3. Why is a plan that “looks reasonable” not necessarily a valid plan?**
An LLM is a text-generator; it wants to output text that *sounds* good to a human. A plan like "1. Move to B, 2. Move to C, 3. Drop package" looks perfectly normal at a quick glance. However, it's completely invalid because the robot forgot to actually pick up the package at step 1! It looks reasonable, but logically, it's a failure. Independent verification catches these hidden mistakes.

**4. What did the LLM contribute to the implementation?**
The LLM acted as a fast "translator." We already knew the logic and the rules, but writing out the Python code for Breadth-First Search (BFS) and object-oriented classes from scratch is tedious. The LLM took our abstract ideas and quickly typed out the repetitive Python boilerplate (like `class Action`, setting up `collections.deque` for the queue, and doing set math).

**5. What did you have to verify independently?**
We couldn't just trust that the LLM's Python code worked perfectly. We had to manually verify it by running specific tests to see it in action.
**Example:** We ran an "Impossible Problem" test (Test B) where we took away the robot's ability to pick up the package. If the LLM code was bad, it might have still magically teleported the package to the goal. By running the test ourselves, we proved the code correctly stopped and said "No plan found."

**6. In this laboratory, where is logical reasoning being used?**
Logical reasoning is happening inside the `is_applicable()` and `apply()` functions in our Python code. Before the robot makes a move, the program uses logic to ask "Is this physically possible?" (checking preconditions). After the move, it uses logic to say "What is the new state of the world?" (applying the effects).

**7. How is planning related to the search algorithms studied in the previous module?**
Planning is basically just navigating a giant maze (a search problem). 
**Example:** Think of the "maze" as a map of every possible situation the robot could be in. The "rooms" are the different states (e.g., Room 1 = robot at A holding nothing, Room 2 = robot at B holding a package). The "doors" connecting the rooms are the valid logical actions. Searching algorithms like BFS just explore this maze, walking through valid doors, until they find the room where the package is safely delivered to C.

### Task 6: Prolog as a Plan Verifier (Page 12)

**Questions:**
- **(a) Why does Prolog return `true` for `can_move(a,b)`?**
  Prolog returns `true` because the query matches the rule `can_move(X, Y) :- connected(X, Y)`. It binds `X=a` and `Y=b`, and then looks for `connected(a, b)` in the knowledge base, which is explicitly defined as a fact.
- **(b) Why does it not establish `can_move(a,c)`?**
  It fails because the rule requires `connected(a, c)` to be true, but `connected(a, c)` is not defined as a fact in the knowledge base (nor can it be derived from any rules).
- **(c) What is the relationship between the Prolog rule `can_move(X,Y)` and the logical implication $Connected(X,Y) \rightarrow CanMove(X,Y)$?**
  They are logically equivalent. The Prolog `:-` operator acts as a reversed implication (read as "if"). So `can_move(X,Y) :- connected(X,Y)` means "CanMove(X,Y) is true if Connected(X,Y) is true", which is $Connected(X,Y) \rightarrow CanMove(X,Y)$.

### 7.2 Prolog Reflection (Page 14)

**1. What is the difference between a Prolog fact and a Prolog rule?**
A fact is an unconditional, fundamental truth asserted in the knowledge base (e.g., `connected(a,b).`). A rule is a conditional truth that defines how new facts can be inferred from existing ones (e.g., `can_move(X,Y)` is true *if* `connected(X,Y)` is true).

**2. How does a Prolog query correspond to asking whether something follows from a knowledge base?**
A query asks the Prolog engine to use its execution mechanisms (unification and resolution/backtracking) to determine if the queried statement can be logically derived from the set of facts and rules provided in the knowledge base.

**3. Why might it be useful to use a Prolog program to verify a plan generated by a Python program?**
While Python is general-purpose and the generated Python planner might contain state-manipulation logic bugs, Prolog is explicitly designed around formal logic. It evaluates rules declaratively, ensuring the verification relies purely on strict logical entailment rather than potentially buggy procedural code.

**4. What advantage does an independent verifier provide when the original plan was generated with the help of an LLM?**
An independent verifier breaks the trust dependency on the LLM. Since LLMs operate probabilistically and can hallucinate plausible-sounding but invalid solutions, using a strict, deterministic logical verifier ensures absolute correctness without relying on the opaque internal process of the LLM.
